# 虚拟主播游戏馆总计划

## 1. 产品目标

让喜欢虚拟主播的玩家在一个网页游戏馆中选择经营、故事、卡牌、推理、节奏或合作玩法。首要目标是每款游戏单独成立；长期成长通过本命展示、纪念物和个人记录连接各游戏。

目标玩家分两类：独自游玩的角色爱好者与策略玩家；偶尔约朋友的轻度合作玩家。默认优先满足前者，单人作品无需凑人、登录、每日签到或购买其他游戏内资源。

成功假设：玩家会因某款游戏本身愿意再玩，也可能因纪念物和角色转向第二款游戏。上线后观察开始到结算的转化、主动重开、存档回访和跨游戏访问；不在无样本时承诺留存率。试玩记录必须区分真人、自动化和开发者。

## 2. 已知基础与待核实项

2026-10-11 阅读了根 README、arena/README、rpg/README、survival/README、index.html 的收藏代码、部署配置和既有 tasks 文件。

- 根 index.html 为既有自走棋主体，含全局状态、17 项成就、本地角色收藏及本命标记。不要把它当新游戏公共运行时。
- 已有 arena.html、online.html、survival.html，以及 rpg/ 独立原型。各模式机制和存档独立。
- 现有 50 人角色与技能资料可作资源来源；各文档对衣装是否启用存在历史差异，实际可用名单和素材由实施前清点确定。
- 幸存者使用本地 Phaser，其他界面以静态网页为主；新游戏默认静态 HTML/CSS/ES modules，不强制全站迁移框架。
- 静态部署使用 Cloudflare 配置，在线服务另有 CloudBase。具体 SDK、认证和服务部署方案应在实施时根据官方文档和现状确认，本计划不锁定未验证的接口。
- 竞技场文档说明无跨设备账号绑定；其凭证代表一局，不能直接升级成玩家账号。
- `tasks/plan.md`、`tasks/todo.md` 是已有八人联机工作；本计划使用本目录的 tasks，不改旧任务。

## 3. 游戏组合

| 项目 | 独立核心循环 | 首版目标时长 | 关键风险 |
|---|---|---|---|
| G1 今晚谁来播 | 排档期—处理事件—经营结算—准备联合演出 | 四周战役约 25–40 分钟，可中断 | 经营只有数值增长，没有选择 |
| G2 下播后的便利店 | 备货—接待—推荐商品—故事变化 | 七夜约 35–60 分钟，可逐夜玩 | 对话重复、经营打断故事 |
| G3 联动大乱斗 | 房间—三种短游戏—积分—总颁奖 | 6–10 分钟 | 网络公平、人数不足 |
| G4 直播事故处理中心 | 分工—描述现场—共同排障—结算 | 教学 3 分钟、正式局 8 分钟 | 信息不对称被破坏、随机题无解 |
| G5 弹幕地下城 | 选路线—打牌—选奖励—调整牌组 | 15–25 分钟，可节点存档 | 唯一最优流派、规则难读 |
| G6 星夜调查社 | 调查—证词—证据矛盾—提交推理 | 单案 20–35 分钟 | 猜作者意图、软锁 |
| G7 返场！ | 校准—选曲—节奏输入—演出评价 | 每曲 60–90 秒 | 延迟、音画不同步、素材来源 |
| G8 星台对决 | 选角色—攻防对战—回合结算—街机晋级 | 每场 2–4 分钟 | 固定步进、攻击判定、AI 与动画连续性 |

时长均为设计目标，试玩后调整。各游戏详细范围见上级目录对应文件。

## 4. 推荐架构与目录（拟新增）

```
library/                 大厅、共享角色清单、存档/纪念品适配器
games/studio-manager/    G1
games/midnight-store/    G2
games/collab-party/      G3
games/broadcast-rescue/  G4
games/danmaku-deck/      G5
games/night-detectives/  G6
games/encore-rhythm/     G7
games/star-fighters/     G8
services/game-library/   可选共享云端服务，实施前冻结技术方案
```

每款游戏应能通过自己的 index.html 独立进入。公共模块仅承载角色元数据、存档接口、展示奖励和大厅导航，不抽象八款游戏的回合或战斗系统。

规则与 UI 分离，规则核接受显式动作并返回状态/事件；随机可注入种子。内容以数据文件管理。无动画也能验证核心规则，动画结束不触发第二次结算。

单人首版用本地适配器运行；云服务不可用不能阻止已下载单人游戏。多人采用服务端权威状态，不能通过本地模拟假装真实多人已完成。

## 5. 里程碑与依赖

### M0：资源和合同
完成 P01 清点、P02 共享合同，选择一款单人游戏。产物为可用角色清单、接口草案、可复现检查命令。不要提前开发全套社交服务。

### M1：第一款完整单人游戏
P03 最小大厅和该游戏前三个任务可并行；使用本地存档与占位素材。必须完成开始、决策、胜负/结尾、保存恢复和再开一局。未验证核心乐趣前不批量生产角色故事或插画。

### M2：第二款不同类型游戏与共享纪念物
完成 P04–P06。验证两个游戏各自独立可玩、进度隔离、纪念物汇总与大厅返回。首款为经营时，第二款优先卡牌或推理。

### M3：联网合作
P07 身份与房间协议风险验证 → P08 联网基础 → G4 双人教学 → 正式关。G3 复用已验证的连接生命周期，保持自己的规则核。账号同步与公开社交不是此阶段的强制前置条件。

### M4：后续扩充
G6/G7/G8 及剩余单人作品按试玩反馈进入制作。G8 以单人对 AI 为首版，不依赖 M3 联网阶段；先用木桩验证格斗规则再制作角色动画。P09 跨设备档案、P10 可选分享展示在本地恢复和奖励可信度明确后实施。

每两个任务形成可运行检查点；任务的确切依赖、负责目录、验收与验证方法在 [todo.md](todo.md)。建议一次只启动一个高风险联机任务和一至两个独立单人任务。

## 6. 跨项目约束

- 保留现有入口和存档键，先新增 library/ 入口；首页链接、sw.js、.assetsignore、wrangler.toml 仅由集成负责人修改。
- 不为新游戏加载整份旧 index.html 获取角色。导出数据清单，保留稳定 ID 与来源路径。
- 不共享可消耗战斗货币，不设跨游戏属性加成，不以其他游戏通关作为开玩条件。
- 不默认加入抽卡付费、体力、强制签到、开放聊天、语音采集、复杂公会或跨游戏大经济系统。
- 角色与音频按需加载，单款游戏首次进入不得下载全部游戏资源。离线能力必须在实际断网与重载测试后才标注。
- 本地成绩可修改；共享页面标注本地记录，不能直接进入可信排行榜或产生可交易权益。
- 按游戏保存 rulesVersion/contentVersion/saveVersion；旧存档不静默清空，迁移失败提供导出与明确说明。

## 7. 默认决策与调整触发

所有项目允许使用 AI 重新生成美术资产，详见 [统一美术方案](../09-ai-art-policy.md)。既有素材可选复用；各游戏文档中的复用建议不是硬性限制。角色动画、场景、UI、道具与特效均可重新设计，先完成游戏内样本验证，再批量扩充。

默认沿用网页/PWA、简体中文、鼠标/触屏，键盘适配到具体玩法。游戏馆名称与游戏标题均为工作名。无需为每个默认项重新询问用户。

当现有素材不适合某玩法时先用合法占位素材验证，再提交具体缺口表；涉及新付费服务、真实上线或改变产品方向时再按实际授权处理。新框架、数据库与实时服务架构由 expert 依据证据选定，不因本文目录建议强行迁移项目。

## 8. 验证与完成定义

每款达到：规则测试覆盖核心失败边界；真实浏览器完成主路径；390×844 与 1440×900 可操作；刷新、暂停/后台、音效偏好和坏存档行为明确；提供截图、执行命令、结果、剩余问题。

G4/G3 另验证两个独立浏览器身份、重复请求、掉线重连、房间过期和隐藏信息隔离。G7 另验证输入时间与音频时钟及设备校准。新入口不得破坏既有游戏导航和存档恢复。

只有计划验收通过才能标记对应任务完成。测试通过不等于数值平衡或内容有趣；至少记录一次真人试玩的困惑点、退出点和想重玩的原因。发布前未做真人验证时必须如实标记。
